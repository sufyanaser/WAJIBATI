# School Master Data

## الهدف

يوفر هذا المسار تحديثاً مركزياً وآمناً لبيانات المدرسة من قالب Excel واحد، مع فصل بيانات التعريف عن Supabase Auth. لا يحتوي القالب على PIN أو كلمات مرور ولا ينشئ مستخدمي Auth تلقائياً.

## سير العمل

1. ينزّل مالك النظام القالب من لوحة الإدارة.
2. يملأ الأوراق مع الحفاظ على `external_key` ثابت لكل سجل.
3. يرفع الملف للمعاينة. تُفحص الحقول والمراجع والتكرارات من دون تغيير قاعدة البيانات.
4. تُحفظ المعاينة كدفعة `previewed` مرتبطة بالمالك وببصمة SHA-256 للمحتوى.
5. يضغط مستخدم بدور `owner` زر التطبيق. ينفذ RPC واحد المعاملة كاملة ويكتب سجل تدقيق.
6. إعادة تطبيق الدفعة نفسها تعيد نتيجة idempotent ولا تنشئ نسخاً مكررة.

## الأوراق

| الورقة | الغرض |
|---|---|
| `subjects` | المواد وألوانها وترتيبها |
| `teachers` | المدرسون وربطهم بالمواد |
| `sections` | العام والمرحلة والفرع والشعبة |
| `timetable` | الشعبة واليوم 0–4 والحصة 1–6 والمادة والمدرس |
| `students` | الطلاب وربطهم بالشعب |
| `guardians` | أولياء الأمور وأرقام الهواتف فقط |
| `guardian_students` | علاقة متعدد لمتعدد بين الطلاب والأولياء |
| `accounts` | بريد الحساب واسمه ودوره كبيانات تعريف فقط |

## الحسابات والصلاحيات

`school_account_profiles` يحتفظ ببيانات الحساب التنظيمية (`owner`, `editor`, `viewer`) ويمكن ربطه لاحقاً بـ`auth.users` عبر `auth_user_id`. إنشاء المستخدم أو دعوته أو ضبط وسيلة دخوله يتم في مسار Auth منفصل ومصرح به. لا تُنسخ الأسرار إلى Postgres أو Excel أو Git.

## التحديث والحذف

- غيّر الاسم أو الهاتف أو الدور مع إبقاء `external_key` نفسه لتحديث السجل.
- استخدم `active=false` لتعطيل سجل مع الحفاظ على التاريخ.
- لا تغيّر `external_key` إلا عند إنشاء كيان جديد فعلاً.
- المراجع مثل `subject_key` و`section_key` يجب أن تشير إلى مفاتيح موجودة في الملف.

## الإنتاج

الـmigration والدالة لا تُطبقان تلقائياً عند الدمج. سير عمل `Supabase Deploy` يدوي (`workflow_dispatch`) ويجب تشغيله فقط بعد مراجعة الـPR، أخذ نسخة احتياطية، وتجربة القالب في بيئة غير إنتاجية. ترتيب التطبيق: migration ثم نشر `import-school-master` ثم اختبار preview ثم apply بملف تجريبي.
